# Pandya.ai Comprehensive Game Authoring Guidelines

Welcome to the **Pandya.ai Game Authoring Guide**. This document is a complete instruction set for LLMs and AI Assistants to develop a new multiplayer game using the Pandya.ai framework. It covers the core pillars of a game: Canvas configuration (visual layout & GDL UI theme tokens), Lua logic (rules and state machine), and Gameplay Instructions (`INSTRUCTIONS.md`), along with MCP tools to validate everything.

---

## 1. Development Workflow (MCP Tools)

When instructed to create a game, follow this workflow using the available MCP tools:

1. **Scaffold the Game**: Use the **`create_game`** MCP tool. (Note: It is `create_game`, *not* `scaffold_game`). This will set up the game record with template files for the core components (`canvas.json` with UI themes, `logic.lua`, `INSTRUCTIONS.md`).
2. **Fetch UI & Logic References**:
   - Use **`get_ui_components`** to retrieve available React UI component primitives (`<Deck />`, `<Dice />`, `<PlayingCardHand />`, `<Tile />`, `<Pawn />`, `<Rondel />`, `<TechTree />`) and GDL Theme Catalog presets (`glassmorphic_dark`, `classic_wood`, `cyberpunk_neon`, `minimal_light`, `retro_arcade`).
   - Use **`get_lua_libraries`** to inspect available Go-Lua engine hooks, state variables, and `util.random()` RNG functions.
   - Use **`get_authoring_guidelines`** to fetch system prompts and schema guidelines.
3. **Define Visuals & Themes**: Write the layout, pieces, zones, and `ui` theme tokens in `canvas.json` (Game Definition Language).
4. **Write Rules**: Implement the game state machine in `logic.lua`.
5. **Write Player Instructions**: Create or update `INSTRUCTIONS.md` (via **`update_game`** tool with `instructions_markdown`) to provide a friendly, plain-language "How to Play" manual — goal, board (include a `{{BOARD_DIAGRAM}}` placeholder line so the platform embeds a real board picture), pieces, setup, turn flow, an example round, and a printable quick reference. Follow the structure and tone in `docs/prompts/INSTRUCTIONS_AGENT_PROMPT.md`; never reference action IDs or engine internals.
6. **Validate & Simulate**: 
   - Use **`validate_game_code`** to ensure your GDL action definitions match your Lua `get_actions` and payload parameters exactly, and validates the canvas JSON.
   - Use **`simulate_game_logic`** to run a headless test in the Lua VM to verify that your script is free of runtime errors and functions correctly.

## 2. Defining Visuals (`canvas.json`)

The Canvas JSON defines the physical setup of the game board. 

### Structure Example
```json
{
  "name": "Tic-Tac-Toe",
  "players": {
    "min_players": 2,
    "max_players": 2
  },
  "board": {
    "type": "BOARD_TYPE_GRID",
    "width": 3,
    "height": 3,
    "disable_rotation": true
  },
  "ui": {
    "theme": "glassmorphic_dark",
    "disable_board_rotation": true
  },
  "pieces": [
    {
      "id": "piece_x",
      "name": "Player X Token",
      "visual": { "shape": "cross", "color": "#0000ff" }
    }
  ],
  "setup": {
    "zones": [
      {
        "id": "main_board",
        "layout": "grid",
        "layoutConfig": { "rows": { "numberValue": 3 }, "cols": { "numberValue": 3 } }
      }
    ],
    "entities": []
  },
  "variations": [
    {
      "id": "variant_large",
      "name": "5x5 Board Expansion",
      "description": "Play on a larger board.",
      "board_config_override": {
        "width": 5,
        "height": 5
      },
      "setup": {
        "zones": [
          {
            "id": "main_board_large",
            "layout": "grid",
            "required_variations": ["variant_large"]
          }
        ]
      }
    }
  ]
}
```

**Key Elements (Defined in `GDL` Protobuf Schema)**:
- **`players`**: Configuration for `min_players` and `max_players`.
- **`pieces`**: Defines archetypes for pieces (`id` is crucial for spawning these in Lua).
- **`setup.zones`**: Contains the physical layout areas.
  - Valid `layout` options: `grid`, `hex_pointy`, `hex_flat`, `fan`, `stack`, `deck`, `free`.
- **`setup.entities`**: Initial piece instances placed in zones automatically at load. **CRITICAL INSTRUCTION**: You MUST populate this array for all physical piece instances and card instances that start in the game (e.g. all 56 cards in a card deck, Chess pieces, starting tokens). For decks or piles, group them into their starting zone by setting `"currentZoneId"` (e.g. `"draw_pile"`). Do not optimize or truncate by generating only a single deck marker entity; generate all individual card/piece entities explicitly as SpatialEntities grouped in their starting zone.
  - **Placement quality**: Prefer typed layouts (`grid`/`fan`/`stack`/`deck`/hex) with a `layoutConfig` so the engine auto-positions entities. For `free` layouts or free-floating entities, spread pieces evenly: they must not significantly overlap (more than half the smaller piece's area), must stay inside their parent zone bounds, and must not cluster 4+ pieces into a tiny area. The generator validator fails (warns) on such broken placement, so re-layout before saving.
- **`ui.disable_board_rotation` / `board.disable_rotation`**: Set to `true` for shared board games (e.g. *Settlers of Catan*, *7 Wonders Duel*, *Carcassonne*, *Ticket to Ride*). This keeps the main board in a fixed, static perspective for all players instead of flipping 180° on turn changes.
- **`variations`**: Allows defining game modes (like expansions) that override the base `players`, `board`, `setup`, and `pieces`. Elements can be locked to a variant using the `required_variations: ["variant_id"]` string array.

### Implementing Graph or Node-Based Boards (e.g. Dash-guti, Alquerque, Nine Men's Morris)
For games with non-standard graph topologies (interconnected nodes and lines, like an hourglass shape):
1. **Canvas Serialization (`layout: "free"`)**: Set the zone's layout to `free`. Standard grid math won't apply. You MUST encode the node coordinates and connections using the top-level `board.paths` array in the GDL. Each `BoardPath` should represent an edge or line segment between coordinates. This ensures the generic visualizer can automatically draw the graph natively.

**Example `paths` configuration in `canvas.json`**:
```json
  "board": {
    "type": "BOARD_TYPE_GRID",
    "width": 5,
    "height": 5,
    "paths": [
      {
        "id": "center_cross",
        "coordinates": [
          {"x": 0, "y": 0},
          {"x": 2, "y": 2},
          {"x": 4, "y": 4}
        ],
        "repeat_per_player": false
      }
    ]
  }
```

2. **Dynamic Lua Validation**: Do not hardcode adjacency maps! Instead, leverage the injected `paths` API. In `on_move`, validate if a target node is reachable by checking if it exists adjacent to the source node along any of the defined paths (e.g., using `paths.get_nodes(path_id)` or `paths.advance(path_id, cell, 1)`).

## 3. Game Logic (`logic.lua`)

The Lua script controls rules, validations, state transitions, and win conditions. It executes in a sandboxed Go-Lua VM.

### Available APIs
The Lua environment has access to the game context (`ctx`), `game`, `paths`, and piece APIs, providing the following capabilities:

- **`ctx.state`**: Access and mutate the board state. E.g., `ctx.state.get_zone("zone_id")`, `ctx.state.get_piece("piece_id")`, `ctx.state.add_piece(piece)`.
- **`ctx.state.vars`**: Access or mutate global game variables. E.g., `ctx.state.vars.current_turn`.
- **`ctx.random`**: Deterministic PRNG for dice rolls (`ctx.random.roll(min, max)`) and shuffling.
- **`ctx.current_player`**: Identify whose turn it currently is.
- **`ctx.log`**: Structured logging for debugging game logic.
- **`ctx.end_turn()`**: End the current player's turn natively.

**Advanced Mechanics (`game` API & State Redaction):**
- **`game.get_variation()`**: Returns the active variation id string (or `"default"` when no variation is active). `game.get_variations()` returns the list of all active variation ids. Test for a specific variant with `game.get_variation() == "variant_id"` — note `get_variation` takes no arguments.
- **`game.queue_action(player_index, move)`**: Queue deferred or simultaneous actions.
- **`game.execute_queue()`**: Resolve all queued actions in round-robin order.
- **`game.set_current_player(player_index)`**: Mutate the standard turn order (e.g., skip, reverse).
- **`game.place_piece(def_id, pos, owner_index)`**: Creates a piece. **`pos` is a board cell coordinate string (e.g. `"1,2"`), NOT a zone id.** Passing a reserve/hand zone id registers the piece as detached from any cell — this is the intended way to model off-board reserve pieces: the engine records a friendly sim-log note (`place_piece: registered ... at off-board zone <pos>`) rather than failing, and cell-based moves will find no valid target on it. To model pieces that start off the grid (reserve/hand) and are later placed onto cells, register them with a non-cell string and then `game.move_piece(piece_id, "col,row")` onto a real cell. (Off-grid pieces have no cell mapping.)
- **`game.move_piece(piece_id, target_cell)`**: Move an existing piece to a cell coordinate string (e.g. `"2,2"`).
- **`piece.set_attr(piece_id, "hidden", true)`**: Redact piece position/properties from opponents (native Fog of War).

**Paths API (`paths`):**
- **`paths.advance(path_id, cell, steps)`**: Advance a piece along a predefined GDL path.
- **`paths.get_nodes(path_id)`**: Returns all cell coordinates in a path array.
- **`paths.get_node(path_id, index)`**: Get the coordinate string at a 1-based index.
- **`paths.get_index(path_id, cell)`**: Returns the 1-based index of a specific cell coordinate in the path.

*Tip: Use the `get_lua_libraries` MCP tool to fetch the full `INTERNAL_ENGINE.md` reference.*

```lua
-- 1. Initialize variables and starting state
function on_setup(ctx)
    ctx.state.vars.current_turn = "player_1"
    ctx.state.vars.moves_made = 0
end

-- 2. Define the allowed action strings declared in the GDL actions list
function get_actions(ctx)
    return { "place_piece" }
end

-- 3. Process an incoming move
function on_move(ctx, move)
    -- move payload structure is defined by the GDL action
    if move.action_id == "place_piece" then
        if ctx.state.vars.current_turn ~= move.player_id then
            error("Not your turn!")
        end
        
        local cell_idx = move.args.cell_index
        local template_id = move.player_id == "player_1" and "piece_x" or "piece_o"
        
        -- Place piece
        ctx.state.get_zone("main_board").add_piece({
            template_id = template_id,
            cell_index = cell_idx
        })
        
        -- Update State
        ctx.state.vars.moves_made = ctx.state.vars.moves_made + 1
        ctx.state.vars.current_turn = (move.player_id == "player_1") and "player_2" or "player_1"
    else
        error("Unknown action: " .. move.action_id)
    end
end

-- 4. Check for terminal states (Win/Loss/Draw)
function check_win_condition(ctx)
    if ctx.state.vars.moves_made == 9 then
        return { is_draw = true } -- Return nil if the game should continue
    end
    return nil
end
```

## 5. End-to-End Validation Standards

When adding or modifying a game, you MUST verify the entire data, logic, and action pipeline. The system enforces strict validation checks (`internal/gameauthor/validator.go`) that all authored code must satisfy:

1. **Structural Integrity**: All serialization paths (Go structs like `UIPiece`, `UIGameState`) must preserve all required data fields (e.g., `properties`, `variables`). NEVER strip metadata needed by UI components during the translation from Lua engine to JSON.
2. **Action Mapping & Consistency**: The action ids declared in the `actions` list of `canvas.json` must match those returned by the Lua `get_actions()` block, and `on_move` must handle every one of them. The static validator extracts the ids from `get_actions()` and asserts the GDL list agrees.
3. **Simulation Verification**: Game logic (Lua) is verified via simulated gameplay. The script must execute without errors, and pieces must be actively placed or moved.
4. **Flat Payload Structure**: Custom moves must pass parameters as flat dictionaries. Do not wrap parameters under a nested `payload:` object.
5. **Naming Conventions**: Enforce snake_case for state fields and property accesses. Avoid PascalCase references (e.g., `.DefinitionID` or `.OwnerIndex`) which cause JSON deserialization mismatch.
6. **Setup Variable Population**: If using `deck.draw` or `hand.add_card` rules in Lua, hand variables (e.g., `zone_hand_X`) must be populated with items during the setup phase.
7. **Strict Canvas Referencing**: Any piece type, zone id, or piece definition your Lua refers to MUST be explicitly defined in the Canvas Data JSON (`canvas.json`). The static validator rejects references to `definitionId`s that do not exist.
8. **Report Winners From `check_win()` Only**: Lua scripts must NOT `game.set_var("winner", ...)` or any other engine-reserved name (`game_over`, `draw`, `current_player`, `turn`, `active_player`); engine variables leak Lua sentinel defaults (e.g. `-1`) downstream. Report the result from `check_win()` and nowhere else.
9. **Playable Hands & Response Cards (CRITICAL)**: Every card dealt into a hand during setup or drawn during play MUST be playable and handled in `on_move`. Give every hand-visible template an explicit `card_type` property and branch on it in the play-card logic so no card yields "unknown card type". Response/defuse-only cards (e.g. a Sanjeevani-style savior consumed when a lethal card is drawn) must NOT be targetable by the general play action — the headless simulator targets every hand card with the play action, so such cards must be filterable or explicitly handled, not rejected as unplayable.
10. **Turn Progression & Simulator Feedback (CRITICAL)**: Every game MUST expose at least one action that reliably advances the turn when legal (e.g. an explicit `endTurn` button that calls `game.end_turn()`); the simulator intentionally executes button actions to progress forced-turn games and will otherwise report a failing pass. The simulator reports the CURRENT player's real failure reason (e.g. "Unknown card type", "Not adjacent! ..."), so fix the underlying rules/canvas named by the error instead of retrying the same logic.
